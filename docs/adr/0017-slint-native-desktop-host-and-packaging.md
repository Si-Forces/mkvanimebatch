# 0017. Slint Native Desktop Host and Packaging

> **Status**: Accepted (port in progress from P0, #133; the Tauri host ships until the switch; amended 2026-10-23 three times)
> **Date**: 2026-10-22
> **Context**: Desktop Application Context
> **Supersedes**: ADR-0007 and ADR-0015, at the switch; ADR-0007's engine-bridge rules carry over in decision 9
> **Amends**: ADR-0016, at the switch

## Context

Issue #102 replaces the WebKitGTK webview with a native Rust toolkit. The webview cannot draw the glass of Redesign C (the Library + Inspector redesign, PR #92) on the target laptop (Intel HD 4000, Mesa 26.2, KWin 6.7 Wayland): `backdrop-filter` drops it from 54 to 14 fps, so v1.x fakes the glass. It also brings the per-package WebKitGTK workarounds of ADR-0015 and an 82.6 MB AppImage that mostly carries GTK and WebKitGTK. ADR-0016 first moved every UI rule into the toolkit-agnostic Desktop Core, so a native host only renders the View State and sends Intents.

Two toolkits were spiked on that laptop with the same slice: a frameless window with a custom title bar, 1000 real `queue::Row`s with rings and sticky release headers, Redesign C's light and dark tokens, and the glass log drawer over the list. Each run scrolled 6 px per frame for 30 s. The full results are on #102 (comment of 2026-10-22). The ones that decided it:

| | Slint (master 45cb2b3, Skia GL) | iced 0.14.0 (wgpu Vulkan, patched) |
|---|---|---|
| Glass σ30, avg / 1% low fps | 59.7 / 52.2 | 58.9 / 31.0 |
| CPU while scrolling, glass σ30 | 24% | 20% |
| Blur | built in, `Rectangle { backdrop-blur }`, Skia only, from 1.19 | hand-written shader; needs a local `iced_wgpu` patch |
| GPU path here | OpenGL, out of the box | llvmpipe by default; Vulkan only with the patch and `ALLOW_UNDERLYING_NONCOMPLIANT_ADAPTER` |
| 1000-row list | virtualized `ListView` | hand-rolled virtualization (40.8 fps without) |
| Start/close cycles | 60/60 clean | 50/50 clean |
| Release binary | 22.0 MB (8.5 MB zstd) | 9.9 MB (3.5 MB zstd) |
| Accessibility | AccessKit | none |
| Licence | Royalty-free 2.0, GPLv3 or commercial | MIT |

Both flicker while resizing under Xwayland and are smooth on native Wayland. X11 was checked only through Xwayland (spike decision Q87 in the comment on #102), and NVIDIA was not tested (Q86).

## Decision

1. **Slint is the desktop toolkit.** A new workspace crate, `desktop-slint`, is a thin host over `mkv-desktop-core`, as `desktop-tauri` is today: it implements the core's `Publisher` by handing the View State to the Slint models in-process, sends Intents, and owns the native dialogs, the window chrome and the `tracing` subscriber that writes Engine Diagnostics. The dialogs stay on `rfd` with its XDG portal backend, as today, so GTK does not come back with them. It holds no rule of the core. The Desktop Core's API does not change for it; anything the host needs that the core lacks is added to the core.

   **Threads.** `Publisher` is `Send + 'static` and is called on the actor's task, while Slint's properties and models live on the event-loop thread. The host's `Publisher` holds a `slint::Weak` of the window and hands each publication over with `upgrade_in_event_loop`; the actor's thread never touches a Slint property. Publications are coalesced while the event loop is busy: one pending slot holds the newest View State, kept only if its `seq` is newer, so a blocked loop applies the latest state once instead of a queue of them. The models are kept, not rebuilt: a mode's rows are reset only when its `manifest_rev`, length or row ids change, and otherwise only the rows whose values changed are set, as the webview's patch did. The dialogs run off the event loop (on a worker thread or through the portal's async API) and send their result back as an Intent, so a dialog never stalls rendering. The spike measured rendering with a synthetic row churn, not this mapping at 15 Hz, so the port measures it.

2. **Releases wait for Slint 1.19 stable.** `backdrop-blur` first ships in 1.19. Until 1.19 is out, the port builds against a pinned Slint master commit, and no release ships it. Release builds take Slint from crates.io with an exact pin (`=1.19.N`), never a git dependency, because the host uses the `unstable-winit-030` feature, which Slint's semver does not cover. The pin is a joint pin of the crate and that feature: the minimize workaround (decision 4) is checked against the feature at 1.19, since the feature can be renamed, dropped or moved to a newer winit in any release. A Slint upgrade is a deliberate change that is checked against the criteria in decision 8.

3. **Skia on OpenGL renders; the software renderer is the fallback.** Slint's default features include FemtoVG and the system tray, so the host turns them off and names its features: `default-features = false` with `std`, `compat-1-2`, `backend-winit`, `renderer-skia-opengl` (Skia on OpenGL only, the path the spike measured; plain `renderer-skia` may pick another GPU API), `renderer-software`, `accessibility` (which turning the defaults off would otherwise drop) and `unstable-winit-030`. When OpenGL cannot be initialized, it falls back to the software renderer, draws the faked glass the webview draws today, and logs one warning through the host's `tracing` subscriber. FemtoVG is not shipped: it works here but cannot blur. The Skia software renderer is not used, because it never drew a frame in the spike. The fallback mechanism (backend selection at startup, or a retry after a failed window creation) is settled in the port; the spike's software renderer (84% CPU while scrolling) is the reference it is measured against.

4. **The window is frameless and native Wayland is preferred.** The title bar is the app's own (`no-frame`, `WindowMoveArea`, `resize-border-width`), as in Redesign C. winit uses Wayland when the session has one, and the host sets no backend default such as `WAYLAND_DISPLAY` or `WINIT_UNIX_BACKEND` (the Tauri host's `GDK_BACKEND` default leaves with `init_linux_env`): Xwayland flickers while resizing and is accepted as it is. Minimize calls winit's `set_minimized(true)` through `WinitWindowAccessor`, because on Wayland winit cannot report the minimized state, so Slint's cached `minimized` stays set after a restore: it drops every minimize after the first and blocks the maximized sync. The workaround stays until Slint fixes it; the bug is reported upstream when the port starts.

5. **Licence: Slint Royalty-free 2.0, met with the badge.** The repo stays MIT. Of the licence's two attribution options, the app uses the second (§2(b)), the Slint attribution badge on a public web page: the README as rendered on the repository page is where it is anchored, and every release body, where the binaries are downloaded, carries it too. The release body is generated by `scripts/release-body.sh`, so the badge and the attribution line are part of that script's page from the first release that ships Slint binaries, pre-releases included (decision 8). The AboutSlint widget (§2(a)) is not required. The app is a desktop application, so the licence's embedded-systems limit does not apply. The host uses Slint's API internally, and the distributed app exposes none of it to third parties, as §3's limit on exposing the API requires. GPLv3 was not taken because it would relicense the app; the commercial licence buys nothing here.

6. **The two hosts live side by side until parity, then one release switches.** While the port runs, `desktop-tauri` keeps shipping. The Slint binary is named `mkv-anime-batch-slint` meanwhile, so the two packages' binaries do not collide in the shared `target/`. Parity means every feature of the shipped Tauri app, on Linux and Windows, and the gate of decision 8 passed on a release build. The features include, without the list being exhaustive: both modes, the Library and the Episode Inspector, the folder and subtitle pickers, the settings and presets, the Run Log with Copy, the `Clear inspection cache…` action and its confirmation, telemetry, the custom title bar, and the light and dark themes following the system with the manual toggle kept. The switch release then renames the binary `mkv-anime-batch`, keeps the identifier `com.mkvanimebatch.desktop`, and deletes `desktop-tauri` with its webview UI, its Node tests, the webview transport (`view_patch.rs`, the patching `Publisher`) and the Linux environment workaround (`init_linux_env`, `apply_linux_env`, `HOST_WAYLAND_CLIENT_CANDIDATES` and their serialised test).

   **Tests.** The UI logic the Node tests covered already moved to Rust with ADR-0016, so what they still cover is the webview's own code: its rendering, its transport (`view-patch.js`, which the S4b amendment keeps out of UI logic), and its bootstrap and platform detection (`theme-init.js`, `os-detect.js`), all of which leave with it. The Slint host's own code (mapping the View State into Slint models, the renderer fallback, the window chrome) gets Rust tests; how the `.slint` markup is tested (Slint's testing backend, or screenshots) is settled in the port.

7. **Packaging.** Each format gets its own tool, since the Tauri bundler leaves with Tauri. The Tauri bundler also generates the launcher entry and installs the icons today; the Slint host commits its own `.desktop` file and icon set instead, and every Linux format ships them:
   - **deb**: `cargo-deb`, with `depends = "$auto"` so the package declares the shared libraries the binary links, and the `.desktop` file and icons listed in `[package.metadata.deb]` `assets`.
   - **rpm**: `cargo-generate-rpm`, with its automatic requirements for the same reason, and the same files in `[package.metadata.generate-rpm]` `assets`.
   - **AppImage**: `appimagetool` on an AppDir the release job builds: the binary, `AppRun`, the same `.desktop` file and the icon. It bundles no libraries: every shared library the binary links (OpenGL/EGL, Wayland, X11, xkbcommon, fontconfig, freetype, harfbuzz, libstdc++) comes from the host, as for the deb and rpm, so the AppImage's floor is the build runner's glibc and libstdc++ (`ubuntu-24.04`). The 10–12 MB estimate assumes this (the type-2 runtime, the binary and the desktop file).
   - **Windows**, from the switch release (before it, Windows ships the Tauri build as today): unchanged in form: the bare `mkv-anime-batch.exe` and the portable zip. No msi. This narrows #102 and ADR-0016, which named an msi; an installer can be added later without touching this decision.
   - **The build needs a C++ toolchain and the Skia prebuilt.** Skia links libstdc++: Linux CI already gets `g++` from `build-essential`, while a Fedora dev box needs `gcc-c++`. `skia-bindings` downloads a prebuilt Skia at build time; building Skia from source needs clang and Python, and ADR-0010 keeps Python out of dev and CI, so the repo's own builds of `desktop-slint` (dev, CI and release) need that download. A source build of Skia, with clang and Python, stays possible for an offline build outside the repo, but the repo does not support it (Consequences).
   - **CI during the port.** While both hosts live in the workspace, CI and the release job build both: they keep `libwebkit2gtk-4.1-dev`, `libgtk-3-dev` and `tauri-cli` for the shipped Tauri app and add the Skia download on top. `cargo clippy` and `cargo test --workspace` therefore build Slint and Skia beside Tauri for the whole port, locally on the 4-core, 8 GB laptop and in CI; the first build pays the Skia download, later ones its cache. Only the switch release drops the WebKitGTK and GTK packages and `tauri-cli`.

8. **The #102 criteria stay the acceptance gate**, on the release build of each switch candidate:
   - **Glass**, on the target laptop and the OpenGL path (a run that fell back to the software renderer does not count): an average of at least 50 fps and a 1% low of at least 45 fps, measured as the spike did (the glass drawer open over 1000 rows, a 6 px per frame scroll for 30 s after a 3 s warm-up, the frame statistics of the spike's `FrameStats`), with the real core publishing at 15 Hz. The spike's Slint 52.2 passes the 1% low and iced's 31.0 fails it, which is the smoothness the choice rests on.
   - **The title bar**: drag, resize, minimize, maximize and close on Wayland and on X11 through Xwayland (narrowing #102's X11 to what this laptop runs, as the spike did under Q87).
   - **Start and close**: 50 clean cycles of 50 on each of Wayland and Xwayland, and with the software fallback forced, as the spike counted them.
   - **Windows**: on the release build, both modes launch, the folder and subtitle dialogs open, the title bar works, a batch runs to completion and the window closes cleanly.
   - **Accessibility**: one Orca pass over the queue and the settings, since ported labels are not proof that AccessKit works.
   - **Sizes**: the exe, the zip and the Linux packages' sizes are recorded, for information, not as a bound.
   - **NVIDIA**: checked before the switch release on a GitHub pre-release that carries only the Slint packages and is handed to testers (Q86); a pre-release is not a release in the sense of decisions 2 and 6, though it carries the badge (decision 5). A confirmed failure on NVIDIA blocks the switch unless the software fallback engages on its own there and the app is usable.

9. **The engine bridge rules of ADR-0007 carry over.** ADR-0007 is superseded at the switch (Consequences). The following rules carry over to the Slint host through the Desktop Core:
   - **In-process.** `mkv-core` runs in the desktop process, with no sidecar; `mkv-cli` stays a standalone CLI. A desktop run uses the session's shared inspect cache unless its request asks for no cache.
   - **Three streams.** Job Events and the Log Channel stay two channels, and Engine Diagnostics are a third stream: `mkv-core` depends only on `tracing`, and each binary installs its own subscriber. An outcome that changes what a run produces is reported on the Log Channel, never only as an Engine Diagnostic. `mkv-cli` writes Engine Diagnostics to stderr, keeping stdout for `--plan` JSON, `--events` NDJSON and the summary. The default level is `warn`, and `RUST_LOG` overrides it.
   - **Panics are isolated.** A panicking item becomes an `error` outcome while the batch continues; a panic that escapes the pipeline is caught at the bridge's join boundary, which releases the Job Slot and ends the job with an error. The release profile therefore never sets `panic = "abort"`.
   - **Two-phase teardown.** Stop and Close cancel cooperatively, wait up to 2 s, then abort the pipeline task. The waits run on their own thread or the blocking pool, never on the UI thread or a tokio worker. Close shuts out new starts (`begin_shutdown`) before it hands the wait off.
   - **The host's entry points.** The host's close request and the end of its event loop take the place of `close_window` and the `ExitRequested` handler. The desktop's diagnostics log stays at the same path on Linux and Windows, `com.mkvanimebatch.desktop/logs/mkv-anime-batch.log` under the local data directory (`$XDG_DATA_HOME` on Linux, `%LOCALAPPDATA%` on Windows). The host computes it as Tauri's `app_log_dir` does, `dirs::data_local_dir()` joined with the identifier and `logs`, and also writes to stderr; it is still emptied at startup when over 1 MB, and the host logs to stderr alone when the file cannot be opened. A packaged Windows build has no console (`windows_subsystem = "windows"`), so there the file is the only output and losing it loses Engine Diagnostics until the next start; the Windows host therefore says once, in the window, that the log file could not be opened and names its path.

## Considered Options

- **iced**: *Rejected*. It is leaner (MIT, a smaller binary, lower CPU), but on the target laptop it needs a toolkit patch to reach the GPU at all, a hand-written blur whose 1% low stays near 31 fps, hand-rolled list virtualization and driver selection code, and it has no accessibility.
- **Keep Tauri and WebKitGTK**: *Rejected* in #102. The glass cannot run at speed in WebKitGTK on this hardware, and the per-package workarounds of ADR-0015 are a standing regression source.
- **FemtoVG as the renderer**: *Rejected*. It drops the C++ dependency but cannot draw `backdrop-blur`, which was the point of the move.
- **Release on Slint 1.18 with the faked glass**: *Rejected*. Shipping the port on 1.18 and turning the blur on later was offered; the maintainer chose to wait for 1.19 so the first native release already has the real glass.
- **Release on a pinned Slint master commit**: *Rejected*. `Cargo.lock` would pin the commit, but it is not a crates.io release, and the unstable winit API on an unreleased commit is a moving target.
- **Rewrite `desktop-tauri` in place, or ship both hosts in a release**: *Rejected*. In place stops releases for the whole port; two shipped hosts double the support surface.
- **An msi for Windows**: *Declined for now*. The exe and the portable zip stay as they are.
- **`cargo-packager`** (Tauri's bundler as a standalone tool): *Rejected*. It does not build rpm, so `cargo-generate-rpm` would be needed anyway. With per-format tools the deb and rpm metadata live in `Cargo.toml`, and the AppDir is a few files the release job writes.

## Consequences

- **ADR-0015 is superseded at the switch**, its body unchanged. With no WebKitGTK, the DMABUF default, the `GDK_BACKEND` default, the `libwayland-client` preload, their serialised test and `APPIMAGE-RUNTIME.txt` (with the release's check that the AppImage bundles GTK and WebKitGTK) all go. The AppImage and Native Package terms remain packaging formats, but the split no longer decides any rendering workaround, so the note in `desktop-tauri/CONTEXT.md` that points to ADR-0015 moves with the host at the switch. Until the switch, ADR-0015 governs the shipped Tauri app.
- **ADR-0007 is superseded at the switch**, as ADR-0016 and #102 said; its body is unchanged apart from a notice under its header that names what carries over. Its text is about the Tauri host (its commands, `tauri::async_runtime`, `close_window`, `ExitRequested`, Tauri's app log directory); the rules that outlive Tauri are restated in decision 9, so a reader of the Slint host needs only this ADR and ADR-0016. Until the switch, ADR-0007 still governs the Tauri host.
- **ADR-0016 is amended at the switch**, its body unchanged apart from naming ADR-0017 in its Consequences: the webview transport of decision 4 and the S4b amendment (patches, `seq` and `base`, `view-patch.js`) leaves with the webview, decision 10's `dispatch` and `get_state` lose their Tauri command wrappers, the host calling the core's handle directly, and the Node tests of decision 8 are deleted with the webview code they test. The theme stays the view's (decision 12), now Slint's `Palette.color-scheme`.
- The binary is about 2.5 times today's (22.0 MB, 8.5 MB zstd, AccessKit included), while the AppImage shrinks from 82.6 MB to an estimated 10–12 MB and the deb and rpm grow from 4.0 MB to about 10 MB.
- The C++ toolchain and the Skia download are new build requirements, locally and in CI. A distro that builds offline would have to build Skia from source.
- Accessibility arrives with AccessKit; the webview's screen-reader labels (such as each row checkbox's) are ported as accessible labels, not dropped.
- Open risks, carried into the port: NVIDIA and native X11 sessions are untested; one Skia GL first-run stall was seen once in the spike and not reproduced; Xwayland resizing flickers; the unstable winit API ties each Slint upgrade to a re-check; and the release date of Slint 1.19 is Slint's, so the switch waits on it.
- `AGENTS.md`, `CLAUDE.md`, `architecture.md`, `CONTEXT-MAP.md` and `docs/agents/domain.md` describe the Tauri host, and link `desktop-tauri/CONTEXT.md`, until the switch; the switch release rewrites them and moves that glossary with the host.
- `README.md` and `scripts/release-body.sh` also describe the Tauri app until the switch, which rewrites them: the Tauri badge, the WebView2 requirement, the WebKitGTK DMABUF troubleshooting, the Tauri system libraries and build steps, the script's required WebKitGTK, JavaScriptCoreGTK and GTK versions and its AppImage runtime table. "Any distribution" for the AppImage becomes the concrete floor of decision 7: a glibc and libstdc++ at least as new as Ubuntu 24.04's, with OpenGL/EGL, Wayland or X11, xkbcommon, fontconfig, freetype and harfbuzz installed. The README keeps its note that the Windows app has no console, so its log file is the only output.

## Amendment — 2026-10-23 (unsafe_code in the generated UI crate)

**Slint's generated code cannot compile under `unsafe_code = "forbid"`.** Every component `slint-build` generates calls `ItemTreeVTable_static!` (`internal/compiler/generator/rust.rs:2665` at Slint 45cb2b3). That macro comes from the `vtable` crate's `#[vtable]` attribute, which emits it with `#[allow(unsafe_code)]` on the `unsafe impl vtable::HasStaticVTable` it expands to (`helper_crates/vtable/macro/macro.rs:755`). A crate that sets `forbid` cannot lower the lint again, so the expansion fails with the hard error E0453 (`allow(unsafe_code)` incompatible with previous `forbid`), whatever the host's own code does.

**Decision.** The generated UI lives in its own crate, `desktop-slint/ui/` (package `mkv-anime-batch-slint-ui`): its `Cargo.toml`, its `build.rs` (which runs `slint-build` with the pinned fluent style), a `src/lib.rs` that holds only `slint::include_modules!()`, and the `.slint` files. It sets its own `[lints.rust] unsafe_code = "deny"` instead of the workspace's lints, so the generated allow compiles and any other unsafe code is still an error. No hand-written code goes into it. The host crate `desktop-slint` (package `mkv-anime-batch-slint`) depends on it for the generated components and on `slint` (same rev and features) for the runtime API, and stays on the workspace's `forbid` like every other crate. This is the one exception to `forbid` in the workspace. It is not reported upstream for now.

**Rejected.**

- **The whole host crate on `deny`**: it would compile, but the host's hand-written code (the Publisher, the models, the window chrome) would lose `forbid`, so a local `#[allow(unsafe_code)]` there would pass review unnoticed. The separate crate keeps that surface at zero hand-written lines.
- **Waiting for upstream** to stop emitting `#[allow(unsafe_code)]` (or to make the generated `unsafe impl` avoidable): the port cannot start on it, and no Slint release is promised to change it.

## Amendment — 2026-10-23 (CI during the port)

**Decision 7's "CI during the port" is narrowed.** It says CI and the release job build both hosts, and that `cargo clippy` and `cargo test --workspace` build Slint and Skia beside Tauri "locally on the 4-core, 8 GB laptop and in CI". From P0 on:

- **Locally, unchanged.** `jj gate`, the git hooks and `jj gpush` still run workspace-wide, so they compile Slint and download the Skia prebuilt beside Tauri.
- **CI isolates the Slint crates in their own job.** `workspace-checks` runs clippy and the tests with `--exclude` for `mkv-anime-batch-slint` and `mkv-anime-batch-slint-ui`. The `desktop-slint` job lints and tests those two crates on Linux and Windows, with its own cache and timeout. `ci-status` needs it on pull requests and pushes, and accepts it as skipped, which is what lets release verification pass without it. A Skia download or build failure therefore fails one job instead of the Tauri workspace job, and the Tauri job's feedback stays as fast as before.
- **Release verification skips the unreleased host.** `release.yml` calls `ci.yml` with `skip-desktop-slint: true`, so a Tauri release is verified exactly as before P0. No release ships the Slint host before the switch (decision 2), so nothing released goes unverified.
- **The switch restores it.** From the switch release on, release verification builds the Slint host again, and P10 (#143) may fold the separate job back into `workspace-checks`.

## Amendment — 2026-10-23 (renderer fallback)

**Decision 3's fallback cannot be Slint's, and "Skia on OpenGL only" is not what the feature gives.** At Slint 45cb2b3:

- `renderer-skia-opengl` also enables `i-slint-renderer-skia/default` (`internal/backends/winit/Cargo.toml:66-68`), which is `softbuffer` and `wgpu-30` (`internal/renderers/skia/Cargo.toml:45`). wgpu is compiled in, and the default Skia renderer walks its own surface chain, OpenGL → wgpu → Skia software (`internal/renderers/skia/lib.rs:275-288`), logging each failure only through Slint's debug log. On the target laptop, with OpenGL broken on purpose (`__EGL_VENDOR_LIBRARY_FILENAMES` naming a missing file), the P0 host fell silently to Skia on wgpu (Vulkan through Mesa's incomplete Ivy Bridge driver), and with Vulkan broken too (`VK_DRIVER_FILES`) to Skia software, with no warning from the host.
- Slint's winit fallback to another renderer runs only when *creating* the renderer fails (`internal/backends/winit/lib.rs:911-920`). Skia's `new_suspended` and `new_opengl_suspended` always succeed (`internal/backends/winit/renderer/skia.rs:20-54`); OpenGL fails later, when the window is created and Skia makes its surface (`renderer/skia.rs:206-230`).
- That failure is not always returned. When Slint creates the window as the event loop resumes, the error ends the loop and `run()` returns it (`internal/backends/winit/event_loop.rs:111-124`). When it creates it later, in `about_to_wait`, which it does on Linux once its wait of up to 500 ms for the portal's appearance settings is over (`internal/backends/winit/lib.rs:643-664`, `xdg_desktop_settings.rs:17`), it stores the error without ending the loop (`event_loop.rs:257-259`) and idles with no window. On this laptop, Wayland and Xwayland alike, a forced OpenGL failure took the second path: no window, no error, no exit.
- The platform is selected once per process, so a fallback after the first window is a new process.

**Decision.** The host pins the renderer and builds the fallback itself (`desktop-slint/src/renderer.rs`, `main.rs`):

- **Detection.** The host selects the backend with `slint::BackendSelector`, naming both the backend (`winit`) and the renderer: `skia-opengl` (`SkiaRenderer::default_opengl`, OpenGL only, no chain) or `software` (Slint's software renderer). `SLINT_BACKEND` is then ignored. On OpenGL, a rendering notifier marks the first drawn frame, and a 2 s watchdog timer checks whether winit has a window. An OpenGL start fails when no frame was drawn and either `run()` returned an error or the window was missing at the deadline; the watchdog then quits the loop, and `run()` returns the error Slint stored, which the log names (for example "Error creating glutin display …"). The deadline is safe from slow drivers: Skia creates its OpenGL surface on the event loop thread in the step that creates the window, so a slow driver delays the timer as much as the window, and Slint's appearance wait is over by then. An error after the first frame is an ordinary error. Rejected: letting Skia's chain pick (it hides the failure and can land on Skia software), a timeout on the first frame alone (it would kill a slow start that did get its window), and probing OpenGL before the platform (winit allows one event loop per process, and a glutin probe without a window would test something else).
- **Dialog, restart and remembered choice (Q104)**, replacing decision 3's "falls back … and logs one warning". On an OpenGL failure the host asks "The GPU renderer could not start. Restart in software mode?", saying it will remember this and how to undo it. On yes it writes `software` to `renderer` under `dirs::config_dir()/com.mkvanimebatch.desktop/` and re-launches itself; on no it exits with the error logged. When no dialog can be shown at all, it re-launches in software mode without saving and logs why. Later starts with the saved choice go straight to the software renderer, with no dialog. Running on the software renderer logs exactly one warning, sets `Theme.glass` to false for the faked glass (P5/P6 draw it), and is what decision 8's forced-fallback start and close cycles run.
- **The dialog on each OS.** On Windows it is rfd's `MessageDialog` (a `MessageBoxW`). On Linux rfd's message dialog only runs `zenity` and reports a missing `zenity` as Cancel, the same answer as "no", while a KDE session often has only `kdialog`. So on Linux the host runs `zenity --question`, then `kdialog --yesno`, itself, and knows when neither could be shown. This narrows decision 1's "the dialogs stay on rfd" for this one dialog; the file and folder pickers stay on rfd's portal backend.
- **Forcing and undo.** `MKV_RENDERER=software` forces the software renderer. `MKV_RENDERER=opengl` forces an OpenGL start over a saved choice and deletes the saved choice once a frame is drawn; that is the undo. Any other value is ignored with a warning.
- **Re-launch.** The host spawns the same executable with the same arguments and its inherited environment plus `MKV_RENDERER=software` and the guard `MKV_RENDERER_RELAUNCHED=1`, then exits; on Windows this is the only way to re-launch, and on Linux it keeps one code path. Under an AppImage the program is `$APPIMAGE`, since the running binary sits in a mount that ends with the parent, and `argv[0]` is `$ARGV0`, which the AppImage runtime sets. The guard makes a failing child exit with its error instead of asking again, so there is no re-launch loop.
