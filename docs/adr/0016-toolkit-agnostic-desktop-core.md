# 0016. Toolkit-Agnostic Desktop Core Owns UI State

> **Status**: Accepted (S0–S4 implemented; amended 2026-10-15, 2026-10-16, 2026-10-17)
> **Date**: 2026-10-15
> **Context**: Desktop Application Context
> **Amends**: ADR-0001, ADR-0007, ADR-0008, ADR-0009, ADR-0011, ADR-0013

## Context

Issue #102 aims to replace the WebKitGTK webview with a native Rust toolkit (Slint or iced, still to be spiked). Much of the code in `desktop-tauri/ui` is logic rather than rendering: the queue reducer, the job phases, preflight, request building and display formatting. A native rewrite would have to port all of it. Part of it already exists twice: `reduceQueueEvent` in `queue-state.js` and `SnapshotStore::update` in `snapshot.rs` reduce the same `JobEvent`s with different rules, for example on late events, progress for queued items and the final batch status.

## Decision

Before choosing a toolkit, move all desktop UI state and logic except the theme into a new workspace crate, `crates/mkv-desktop-core` (the **Desktop Core**). It depends on `mkv-core` and **not on Tauri**.

1. **The Desktop Core owns the state.** Per mode it holds the Inspection Manifest, the Queue Selection and the Track Assignments. It also holds one Job Snapshot (participants only) and the Job Coordinator's phase. Queue rows are derived by laying the Job Snapshot over the manifest order. The core also runs preflight and builds the `BatchRequest`; a view never builds a request. A view sends user intents and renders what the core publishes.
2. **One reducer.** The reducer preserves the v1 event guard: drop any `JobEvent` whose `version` is not 1 before applying it. Where the JS and Rust reducers disagree, Rust's stricter rules win: drop events that arrive after the batch or belong to another job, apply progress only to processing items with finite values, let `ItemStart` rename the item's file, keep an item's status typed (`ItemStatus`, whose terminal values are the Item Outcomes) rather than a string, and settle the batch status as error when items are left open. There are two exceptions. Default outcome reasons become presentation labels, not stored values. A per-item fallback duration, measured on a monotonic clock like Item Duration, is kept for when `duration_sec` is missing. Outcome counts are derived, not counted.
3. **The core derives every displayed value**: status labels and tone tokens, the batch clock, elapsed times, filter counts and the subtitle ladder text. It also runs the Presentation Heartbeat, a 1 Hz tick that runs only while an item is in flight. A view keeps only toolkit geometry, such as sparkline points and ring arcs.
4. **Publication is whole-state and coalesced.** The core marks itself dirty on each change. The Tauri adapter emits the full view state at most about 15 times a second. A native toolkit reads it in-process.
5. **No reload restore.** The core lives as long as the process, so a webview reload fetches the current state. The Job Coordinator's `restoring` phase and `createQueueStateFromSnapshot` are removed.
6. **The engine tags each log line with its kind.** The Log Channel carries typed lines instead of `String`. Each line has a `LogKind` (`error`, `warning`, `skipped`, `succeeded`, `step`, `cache` or `note`, the plain default) and the text. The kind is chosen where the line is written, and the seven kinds map 1:1 to today's console looks (err, warn, skip, ok, info, done, unstyled). The `[ERR]` prefix, which the desktop supervisor adds today (`job.rs`), becomes CLI and copy-log rendering, and `classifyLine`'s substring guessing goes away. Three severity levels were rejected because they would turn the skipped, succeeded, step and note lines plain.
7. **One seconds-to-ms parser.** The CLI's private `parse_seconds_as_ms` (`crates/mkv-cli/src/args.rs`) moves into `mkv-core` and is shared by the CLI and the Desktop Core. The JS copy, `subOffsetSecondsToMs` (`job-controller.js`, which also rounds half away from zero), is deleted.
8. **Tests move with the code.** Each JS logic test is ported to Rust in the PR that moves its logic, and the JS test is deleted there. The Item Settlement golden fixture, `desktop-tauri/ui/fixtures/settlement-events.json`, is kept by the Rust wording test in `snapshot.rs` once its JS consumers are deleted. Node tests cover rendering only.
9. **The core is one actor task.** It owns the state and has a single inbox for Intents, Job Events, log batches, heartbeat ticks and publish ticks, so every state change happens in one place. The Engine Bridge moves into the core: `job.rs` (Job Slot, supervisor, two-phase stop), `snapshot.rs` (Job Snapshot and Item Settlement, `settlement_events`), `telemetry.rs`'s sampler (`TelemetryState` and `poll`, already Tauri-free; only the `get_system_telemetry` command reads it through an `AppHandle`; it stays a thin adapter command until S4, when the core polls on its own cadence and the command goes away), and the `run_job`/`stop_job` logic in `commands.rs` and `process.rs`. `tauri::async_runtime` is replaced by a plain tokio handle, and the supervisor's `JobSink` feeds the actor's inbox: events and `JobSink::logs` batches both use the actor inbox rather than a separate synchronization path, ensuring log batches queued before a publish tick are appended to the log ring before that tick runs.
10. **Two bridge calls.** A view sends a typed `Intent` enum through `dispatch` and reads the state through `get_state`. Native dialogs (`rfd`) and window chrome stay adapter commands; a picked path comes back in as an Intent.
11. **The log is not part of the whole state.** The core keeps the capped log ring, for copy-log and for a reload, but publishes new lines as appended batches of typed lines.
12. **Also in the core**: each mode's settings draft (which is still not persisted across launches), and the telemetry polling cadence. A `ViewVisible` Intent pauses polling while the window is hidden. **Not in the core**: the theme, which is the toolkit's own appearance.

`desktop-tauri` becomes one thin adapter over the core: `#[tauri::command]` wrappers, the `AppHandle` emit, dialogs and window chrome.

## Delivery

The move ships in five slices, sub-issues of #102. Each slice PR moves its JS tests to Rust.

- **S0**: the Log Channel `LogKind` and the shared seconds-to-ms parser, in `mkv-core` and the CLI.
- **S1**: the `mkv-desktop-core` crate, the Engine Bridge move and the reducer rules.
- **S2**: the actor, Intents, publication, derived queue rows and the Inspection Coordinator.
- **S3**: the Job Coordinator, preflight, `BatchRequest` building and the settings drafts.
- **S4**: presentation values, the Presentation Heartbeat, the telemetry cadence and the log ring.

The toolkit spike starts after S1, so it can render real queue state.

## Considered Options

- **Dedupe the reducers only**: *Rejected*: most of the logic would still be ported by hand during the native rewrite, and avoiding that port is the reason to do this first.
- **Keep state in JS and call Rust for pure functions**: *Rejected*: the two reducers would remain, and a native toolkit renders from Rust state anyway.
- **`Arc<Mutex<State>>` instead of an actor**: *Rejected*: a single inbox keeps every state transition in one place.
- **Per-row deltas to the view**: *Rejected*: rows are small, progress is already throttled upstream, and a native view would not need a diff protocol.
- **Rust→WASM in the webview (Leptos/Dioxus-web)**: *Rejected in #102*: it keeps every WebKitGTK problem and adds a bundler.

## Consequences

- The engine stays in-process. It amends these ADRs:
  - **ADR-0001**: decision 4 (the reducer in the frontend `QueueTracker`), the Inspection Reuse addendum (rebuilding Queue Tracker state from a reused manifest) and the 2026-09-28 amendment (the Queue Tracker rejecting a manifest whose `version` is not 2): all now live in the Desktop Core.
  - **ADR-0007**: its command surface (`run_job` in decision 1 and the 2026-10-04 amendment, `stop_job` in the 2026-10-04 amendment): running and stopping become Intents sent through `dispatch`.
  - **ADR-0008**: decision 4 (`get_job_snapshot()` restoring queue presentation across UI reloads): a reload calls `get_state` instead.
  - **ADR-0009**: decisions 2 and 4 and the 2026-09-28 and 2026-10-11 amendments: the Presentation Heartbeat (formerly in the JS `QueueTracker`), its batch clock redraw, the adaptive duration formatting and the reducer's `item_start` duration fallback move into the Desktop Core, and a webview reload calls `get_state` instead of restoring the Job Snapshot from `get_job_snapshot()`.
  - **ADR-0011**: decision 4: queue selection and reordering in the JS `QueueTracker` become Desktop Core state and Intents.
  - **ADR-0013**: Amendment 11 (2026-10-06): after a webview reload the chips show the Effective Settings from `get_state`, not from a restored Job Snapshot's `effective_settings`, and the frontend tests that cover them move to Rust.
- The toolkit ADR (the spike winner, and packaging for deb/rpm/AppImage/msi) follows the spike, per #102, and supersedes ADR-0007 and ADR-0015.
- The glossary's Queue Tracker, Job Coordinator, Presentation Heartbeat and Job Snapshot now describe Desktop Core components, not frontend ones.
- Several known JS-only bugs go away because the behaviour they live in goes away: `release`/`metadata` lost on restore, and unguarded non-finite progress.
- The Log Channel type change touches `mkv-core`, the CLI and the desktop.

## Amendment — 2026-10-15 (no `[ERR]` rendering)

- **Replaces decision 6's "`[ERR]` prefix becomes CLI and copy-log rendering".** No kind adds a prefix when a line is rendered as text: the CLI and the desktop's Copy write each line's text unchanged. The kind replaces `[ERR]`, which existed only so `classifyLine` could colour the bridge's lines red.
- **Error lines say `ERROR:` in their text**, as the engine's `  ERROR: ...` lines already do. The Engine Bridge writes `ERROR: Pipeline failed: {error}` and `ERROR: Pipeline panicked: {message}`, with no indent since they are not nested under a `Processing:` line, and the webview's own error lines read `ERROR: <message>`. All of them stay `error` lines.
- **Deviations from the old console looks.** Kinds otherwise reproduce what `classifyLine` showed; these three change, and with them the error badge count for the same run (lower for the two warnings, higher for a panic):
  - `   -> WARNING: Failed to promote {label} to ...` (`extract.rs` `promote_optional`) is a `warning`, like `FontPromotion::Failed`, because a failed optional promotion does not fail the file. `classifyLine` coloured it red ("failed" matched first); it is now yellow and no longer counts toward the error badge.
  - The bridge's panic line, `[PANIC] {message}` before and `ERROR: Pipeline panicked: {message}` now, is an `error`. `[PANIC]` matched no rule, so the line was styled only by words in the panic message and was usually plain and uncounted; it is now red and counted.
  - `warning_log_line` lines (Media Tool exit-1 warnings and chapter warnings, `  Warning: <text>`) are `warning` whatever that text says. `classifyLine` coloured them red and counted them when that text contained "error" or "failed"; they are now yellow and uncounted.
- **Why.** Rendering `[ERR] ` before every `error` line doubled the marker on engine lines (`[ERR]   ERROR: Remux failed ...`). With no prefix, the CLI prints every line byte for byte as it did before the Log Channel was typed.

## Amendment — 2026-10-15 (S2: settlement ledger, run and stop, S2a and S2b)

- **The supervisor keeps a private settlement ledger.** Decision 1 gives the actor the one Job Snapshot; the job supervisor also keeps its own per-job `JobSnapshot`, built by the same reducer (`JobSnapshot::apply`) from the same events, settlement events included. It settles the job and computes the `job-done` code from it, so teardown (Stop, Close, `ExitRequested`) never depends on the actor. One reducer, two instances of its state; `SnapshotStore` and its lock are gone.
- **Run and stop stay commands until S3.** `run_job` and `stop_job` remain Tauri commands while request building and preflight are still in JS, and `stop_job` must still resolve only after teardown. S3 turns them into Intents sent through `dispatch`.
- **S2 ships in two parts.** S2a: the actor with its one inbox, the actor-owned published Job Snapshot, coalesced whole-state publication (the ~15 Hz cap lives in the core, not the Tauri adapter as decision 4 phrases it, so a native view gets it too) and `get_state`, with the supervisor's `JobSink` feeding the inbox; the webview is unchanged. S2b: Intents, the queue rows, the Inspection Coordinator and the JS cutover.

## Amendment — 2026-10-16 (S2b: fixture path, unbounded inbox)

- **The Item Settlement golden fixture lives at `crates/mkv-desktop-core/tests/fixtures/settlement-events.json`** (decision 8), now that its JS consumers are gone; the Rust wording test in `snapshot.rs` keeps it. The actor's inbox stays unbounded, with no `Arc<JobEvent>`: the engine already drops `ItemProgress` it cannot send, the actor only applies events in memory and publishes at most about 15 times a second, and a bounded inbox would need async `JobSink` methods, letting a slow actor stall the supervisor's teardown.
- **Older ADRs that name what S2b removed are superseded on those points**, their bodies unchanged: ADR-0001's Desktop Operation Ownership addendum (item 1) and its 2026-10-08 amendment name `inspect_directory`, which the `ScanDirectory` Intent and the Inspection Coordinator replace; ADR-0008's Item Settlement amendment names `guardUnsettledItems`, the fixture at `desktop-tauri/ui/fixtures/` and a JS test of the guard's two constants, all removed: no webview code settles or guards items, and the fixture's only test is the Rust one. The pill rule of that amendment holds through the `job-done` code alone, which is the terminal's status.

## Amendment — 2026-10-16 (S3: S3a and S3b, Settings Drafts, defaults and presets)

- **S3 ships in two parts.** S3a: the Settings Drafts end to end. S3b: the Job Coordinator, preflight, `BatchRequest` building, and Run and Stop as Intents. Until S3b the webview still builds the request from the form, which now mirrors the published draft.
- **A Settings Draft is held as typed** (decision 12): one per mode, every field a string as the user typed it except the dry-run and no-cache checkboxes, parsed by the core only when a run reads it, and still not persisted across launches. The `EditDraft` Intent sets any of its fields and the `SetPreset` Intent puts the remux draft on a Preset Profile; a running job refuses both. A changed bitrate or complexity makes the preset custom, and custom only relabels the form. Because the draft holds the input folder, a webview reload now loses only the run log (S4).
- **Draft Intents are coalesced by the publication cap** and answer without a forced publication, so typing is not one View State per keystroke; the publish-before-reply rule applies to the other Intents.
- **Defaults and the preset catalog are published in the View State** as `defaults` (the Effective Settings of a request that sets nothing, read once on the blocking pool when the actor starts, `null` until then) and `presets`, and the core applies a profile to the draft, so the webview holds neither the catalog's rules nor a copy of it. The `get_default_settings` and `get_preset_profiles` commands are deleted.
- **Older ADRs that name those commands are superseded on those points**, their bodies unchanged: ADR-0013 Amendment 11 and ADR-0008's 2026-10-06 desktop bridge amendment (its Defaults bullet) name `get_default_settings`; ADR-0008's decision 2, its 2026-09-28 amendment (its Preset payload bullet), its 2026-10-06 desktop bridge amendment (its Preset catalog bullet) and its 2026-10-11 amendment name `get_preset_profiles`. The rules they set still hold through the View State: the desktop sends `workers: null` for an empty field and shows the defaults as `auto (N)`, the webview holds no copy of the catalog, the preset id is a label, and the sidebar shows no rows until the catalog is known. ADR-0012 does not name either command. The coverage ADR-0013 Amendment 11 cites moves with the command: `test_default_settings_match_a_resolved_empty_request` (in the adapter's `commands.rs` at S3a, in the core's `control.rs` since S3b) pins that `EffectiveSettings::defaults()` and a resolved empty request agree, with `workers` within 1–16.
- **Run and Stop are Intents (S3b).** `{type: "run", mode}` builds the `BatchRequest` from the mode's Settings Draft and answers when the start settles: `true` once the job launched, `false` when a Stop ended the start before its launch, and otherwise the error, whose text the webview logs as `ERROR: ` and the text. `{type: "stop", mode}` answers after the teardown: `true` when it stopped the job or cancelled the start, `false` when the mode owns nothing, and the teardown's error, which puts the Job Coordinator back to `running` unless the job's `Done` already came. A teardown that fails while the request resolves or the folder scans still ends the start: Stop gets the error, the start ends `cancelled` and Run answers `false`. The core publishes before either answers, and the supervisor sends `done` before its Job Slot guard releases the slot, so `get_state` after Stop's answer shows the job ended. A Done that arrives before the launch returned answers the Run (`true`) and ends the start; the late launch result is dropped as stale, like every message of an ended start (each carries its attempt number).
- **The Stop note follows the published phase.** The webview logs `Stop requested; waiting for shutdown.` when the mode owns the batch and `run.phase` is `running`. The core does not publish a start's steps, so a Stop during the launch step (still `starting`) logs no note; before S3b it did once `run_job` had been called. A start's forced scan whose start ended or is stopping by the time its path resolves inspects nothing.
- **The Job Coordinator is the core's** (`coordinator.rs`): phases `idle`, `starting`, `running`, `stopping` and the owning mode, published as `run: {phase, mode, settings}`, `settings` being the start's Effective Settings from its resolve until the start or the job ends; each ModeView gains `outcome` (`done`, `cancelled` or `failed` from the `job-done` code `0`, `-1` or anything else; a failed start is `failed`, one stopped before its launch `cancelled`; `null` before the first and from a Run's begin). A reload therefore adopts nothing; one during `starting` also loses the Run's answer text (its `ERROR: ` line) until S4 moves the log into the core. `job-done` is still emitted, though the webview no longer listens to it.
- **The busy lock.** The batch is busy while the phase is not idle or a job is active. Busy refuses the queue Intents (`A batch is running; the queue is locked until it ends.`), `edit_draft` and `set_preset` (`A batch is running; the settings are locked until it ends.`; S3a refused them only while a job was active) and a Run (`A job is already running or stopping. Wait for it to finish.`, the Job Slot's text). A Run is also refused while its mode scans (`The folder is being scanned; a batch can start once the scan ends.`). Every user scan, in both modes, is refused while a start is before its launch (`A batch is starting; no folder can be scanned until it has started.`), which protects the start's own forced scan; while a job runs, only a scan of its own mode is refused, as before. These refusal texts are new: the webview refused silently with Run disabled. A sink closed without a `Done` ends the job as `failed`.
- **Preflight is a pure function of the core** (`coordinator::preflight`), run on the start's own forced scan, with the webview's texts unchanged. An empty filtered remux assignment list becomes none instead of an empty list.
- **The Launcher port.** Like the Inspector, `Launcher` (`resolve`, `launch`, `stop`) runs off the actor; `EngineLauncher { job, scan, cache }` in `control.rs` runs `resolve_canonical`, `launch` and `stop_job_inner` on the blocking pool, so the synchronous canonicalize leaves the calling thread. Close and `ExitRequested` still call the teardown directly, never through the actor; `begin_shutdown` makes a Run still in preflight fail at its launch.
- **Request building changes three details.** An extract request sends no preset (the webview sent the active preset row's). The sub-offset goes through `mkv_core::request::seconds_to_ms`, bounded by `i64` milliseconds instead of JS's safe integers, so `1e15` seconds is now accepted, while `abc`, `1e300`, `1e400`, `inf` and `NaN` keep the exact old text (`Invalid sub-offset value '{raw}': must be a number of seconds within range.`); Rust's float syntax also rejects forms JS's `Number` read, such as `0x10`. Complexity, workers, Disk I/O and FFmpeg threads are parsed as whole numbers (an empty field is none, `0` is kept), and a value that is not one gives the new message `Invalid {label} value '{raw}': must be a whole number.`, with the labels `encoder complexity`, `workers`, `Disk I/O` and `FFmpeg threads` and `{raw}` the trimmed value; JS's `parseInt` read `5.7` as complexity `5`, and the other fields failed in serde. Fields are checked in the order input folder, sub-offset, complexity, workers, Disk I/O, FFmpeg threads. A draft that builds no request publishes the field as the draft's `invalid`, answers the Run with the text and changes no phase or outcome; the next edit of that field (or `set_preset`, for complexity) or the next Run clears it.
- **The `run_job`, `resolve_batch_request` and `stop_job` commands are deleted**, and `CoreHandle::job_sink` is crate-private. Older ADRs that name them are superseded on those points, their bodies unchanged: ADR-0007's decision 1 and 2026-10-04 amendment (`run_job`, `stop_job`), ADR-0008's 2026-10-06 desktop bridge amendment (its Resolution before the scan bullet, which adds `resolve_batch_request`: now the start's resolve, before its forced scan), and this ADR's 2026-10-15 amendment (run and stop stay commands until S3). The rules they set hold through the Intents: the request is resolved before the scan, a stop still answers only after teardown, and its two phases are unchanged.

## Amendment — 2026-10-16 (S4: S4a, S4b and S4c; the Run Log and the telemetry cadence)

- **S4 ships in three parts.** S4a: the Run Log, the telemetry cadence and the `view_visible` Intent. S4b: an adapter-side diff of the published state, and `busy` in the View State. S4c: the presentation values, the Presentation Heartbeat, the Episode Inspector's `inspect` Intent and the stepper. Each part has a Rust stage and a JS stage, like S3b. The rest of this amendment is S4a.
- **The Run Log** (decision 11; `log.rs`): one per mode, held with the mode's queue and draft, keeping the newest 2000 lines. `ActorSink` records the job's mode at `started`, and the actor appends each of the job's batches to that mode's log in inbox order (decision 9), the supervisor's `ERROR: Pipeline …` lines included. Each append or clear goes out at once as a `LogBatch` (the `job-log` event): `{mode, generation, first, keep_from, errors, lines: [{kind, text, display?}]}`. `first` and `keep_from` are absolute line indices (of the batch's first line, and of the oldest line still kept), so a view trims what it draws and what it has queued with no cap of its own; `errors` is the Log badge's count of kept `error` lines; `display` is the line with its paths Finder-style, left out when it equals the text. A clear bumps `generation` and restarts the indices at 0. `get_log` (`{mode}`) answers `{mode, generation, first, errors, lines}`, so a reload shows the log again, the `ERROR: ` line of a Run answered during `starting` included. Copy writes the raw lines the view already holds, since awaiting `get_log` before the clipboard write could lose the click's user activation in WebKit.
- **The core writes the lines the webview wrote**, each into the Intent's mode with the same text and kind: `ERROR: ` and the error for every Run answered with an error (a refusal, a draft that built no request, a failed start); the Stop note `Stop requested; waiting for shutdown.` under the rule of the S3 amendment (the mode owns the batch and the phase is `running`); `ERROR: ` and the error once per failed teardown, rather than once per Stop click; and the cache line of the new `{type: "clear_cache", mode}` Intent, which clears the session inspect cache off the actor through the `Inspector` port and writes `Persistent inspection cache cleared.` (`cache`) or `ERROR: ` and the error. No webview code writes a log line.
- **The clear point is the request's resolve.** A Run clears its mode's Run Log, and sends the empty batch, when its request resolves, before `run.settings` is published; the other mode's log is untouched, and a Run refused before it resolves is logged under the earlier lines, as before. The view no longer clears on seeing `run.settings`, so a quick preflight failure whose publication a later `get_state` overtook can no longer leave the old lines up, and lines queued for a frame can no longer outlive a clear.
- **The telemetry cadence is the core's** (decision 12; `actor/timers.rs`): a sample every second while busy (the phase not idle, or a job active) and every 30 seconds otherwise; an immediate one at the actor's start, when busy changes and when the view shows again; none while the view is hidden; never two at once, a poll that falls due during a sample being skipped; a failed sample keeps the last values. `{type: "view_visible", visible}` carries the window's visibility; it has no mode, the core starts visible, and it answers whether the value changed without a forced publication, like the draft Intents. The result is the View State's `telemetry`, `null` until the first sample and then `{cpu, ram, disk, samples: {cpu, ram, disk}}`: the webview's former texts and 40 samples per series, which a sample publishes through the coalesced cap. The view keeps only the sparkline geometry. With the view hidden and nothing in flight, no timer of the core runs.
- **The Sampler port and `Ports`.** The actor samples through a `Sampler` port; `EngineSampler` wraps `TelemetryState` and samples on the blocking pool. `Core::spawn` takes `Ports { inspector, launcher, sampler }` in place of a separate argument per port. `Core` keeps one type parameter per port, since the ports' `impl Future` methods cannot be trait objects.
- **The `get_system_telemetry` and `clear_cache` commands are deleted**, with the adapter's `telemetry.rs` and its managed `TelemetryState`; `get_log` is added. Superseded on those points, their bodies unchanged: decision 9's "it stays a thin adapter command until S4"; decision 11's copy-log reason for the ring (a reload still reads it; Copy uses the view's lines); the S3 amendment's lines that a reload "loses only the run log (S4)" and loses a starting Run's `ERROR: ` line "until S4", and those that name the webview as the writer of the `ERROR: ` and Stop note lines.

### S4b — 2026-10-17 (the view-state patch and `busy`)

- **The webview adapter sends patches.** Decision 4's "the Tauri adapter emits the full view state" is superseded: the adapter emits the first state whole, then patches; its body is unchanged. The core still hands the whole View State to its `Publisher`; `WebviewPublisher` keeps the state it emitted last and emits what changed (`view_patch.rs`). Its first emission is the whole state, with no `base`. Each later one is `{seq, base, ...the changed top-level keys}`, `base` being the previous emission's `seq`, each changed key carrying its whole new value (`"job": null` included). A changed mode carries only its changed ModeView keys, with its rows either whole (`rows`, when `manifest_rev`, the row count or the id at any index changed) or as `row_changes`, `[[index, Row], ...]` by ascending index; an unchanged mode is absent, and a publication that changed nothing is still `{seq, base}`. `get_state` is unchanged and always whole. The webview drops a payload whose `seq` is not newer than the state it applied, applies a whole one, merges a patch whose `base` is that state's `seq`, and otherwise reads `get_state` once, single-flight among these resyncs, and evaluates the patches that arrived meanwhile against its answer. `ModeView.rows` is an `Arc<Vec<Row>>` (serde's `rc` feature, the same bytes), so the adapter's copy and the comparison of an unchanged mode cost a pointer check.
- **The rejection of per-row deltas holds for the core only.** The Considered Options rejected per-row deltas to the view: the core publishes no diff, and a native view reads the View State in-process and needs none. The webview transport may diff in its adapter, as above. `view-patch.js` is that transport's logic, not UI logic: it holds no rule of the core, so decision 8 does not move it.
- **`busy` is in the View State**, the value of the core's busy rule (the phase not idle, or a job active); `isBusy` in `presentation.js` is deleted, and the views read the field. The Node tests' fake core keeps the rule only to set the field, naming `actor.rs` as its source.
- **Pruning `participants` and `start_time_ms` from the Job View moves to S4c**, with the batch clock: until then the webview's clock still reads them.

### S4c — 2026-10-17 (the presentation values, the Presentation Heartbeat, `inspect` and `step_draft`)

- **The core derives every displayed value** (decision 3), in pure functions with their tests: `presentation.rs` for the queue, the list header, the bottom bar and the controls, `inspector.rs` for the Episode Inspector. Each row adds `label`, `tone` (`info`, `ok`, `err`, `mute`), `title` (the hover text), `meta`, `meta_error` and `bucket` (`todo`, `done`, `failed`, or `null` when unselected), and drops `metadata`, `inspection_error`, `start_time_ms`, `duration_sec`, `reason` and `error` from the wire; `status` and `progress` stay for the ring. Each ModeView adds `title`, `crumbs`, `count_text`, `clock`, `progress` (`{done, skipped, failed, live}` in percent, which the view formats), `filters`, `selected_count`, `total_count`, `library` (with each release's `group_label`), `inspector` and `controls`. The default labels decision 2 made presentation values (`Skipped`, `Cancelled`, `Failed`) are the core's constants, no longer supplied by the webview.
- **The wording is the webview's, byte for byte.** The JS tables are ported to Rust tests (decision 8), quirks included and pinned in test comments: the meta line of a failed row with no error reads `Failed · Failed`, and that of a row only the Job Snapshot lists reads `Skipped · Skipped` or `Cancelled · Cancelled` for a skipped or cancelled item with no reason and `Queued` for a planned one. Durations are rounded to tenths before `{:.1}`, so Rust and `toFixed` cannot meet an exact binary tie; `f64::round` and `Math.round` agree on the non-negative values rounded.
- **The controls and the chips are published too.** Each ModeView's `controls` is `{run_label, run_title, run_disabled, owns, stop_label, stop_disabled, selection_locked, status: {class, label}}`, and the View State's `chips` is `{workers, io_jobs, workers_hint, io_jobs_hint}`, the texts and rules `job-controller.js` and `settings-chips.js` held. Only a Run the view sent and has not had answered stays the view's: it locks Run and the settings from the click on, which the core cannot see.
- **The Presentation Heartbeat is the core's** (`actor/timers.rs`). It runs while the batch clock runs (the job is active, its `BatchStart` named at least one item, and its batch has not ended) and the view is visible. Decision 3 says "while an item is in flight"; the batch clock also runs while nothing is processing, so it beats then too. It beats on whole seconds of the job's clock, its start plus k seconds, and a beat only marks the job's mode changed: the labels and the clock are computed when the View State is published, as of then, so every publication shows fresh elapsed times and the 66 ms cap coalesces beats with other changes. Hiding the view pauses it, showing it again refreshes at once, and the batch's end publishes the final labels. With the view hidden and nothing in flight, no timer of the core runs.
- **The clock is monotonic.** `JobSnapshot::apply_at(event, now)` stamps an item's start with the instant it is given; the supervisor's ledger keeps `apply` (`Instant::now()`), and the actor passes Tokio's clock, so a paused-time test moves it. The actor records the job's start on its `JobStarted`, which the batch clock counts from, as the webview's clock counted from `start_time_ms`. A laptop suspend no longer counts toward an elapsed time, consistent with Item Duration.
- **`{type: "inspect", mode, id}`** picks the row the mode's Episode Inspector shows (`null` clears the pick, which shows the first row). It is not refused while busy, since it changes nothing a batch reads, and answers after a publication like the other non-draft Intents: `true` when the pick changed, `false` when it is the same or names a row the queue does not hold. As the webview did, a pick a rescan no longer finds is kept: the first row shows until a rescan brings it back. The `Choose a file…` entry of the subtitle choices stays the view's, since it opens the view's file picker.
- **`{type: "step_draft", mode, field, direction}`** is a stepper click (`sub_offset`, `workers`, `io_jobs`, `ffmpeg_threads`; `up` or `down`), applied as an `edit_draft` of the field and coalesced like the draft Intents. It steps from the field's number, else from the published default behind its `auto (N)` hint, else 0, by one (the sub-offset by half a second, unbounded), clamps to `WORKERS_RANGE`, `IO_JOBS_RANGE` or `FFMPEG_THREADS_RANGE`, and rounds to 10 significant digits. A strict parse replaces JS's lenient `parseFloat`, since a number input holds a number or nothing; exact decimal rounding and `toPrecision(10)` differ only on an exact binary tie at the tenth digit. `stepper.js` is deleted; the view keeps the hold-to-repeat timing.
- **The cached row base.** The part of a row that depends only on the manifest, the Track Assignments and, for remux, the draft's bitrate and assets dir (the name, the release and the meta line) is kept per manifest item and rebuilt only when one of those changes, so a publication only lays the status over it. A draft edit that changes the bitrate or the assets dir therefore marks remux changed, and the patch sends only the rows whose meta line changed; this amends the S3 rule that a keystroke rebuilds no rows, which holds for every other field. The inspector, the controls and the chips are laid over every publication instead, since they follow fields (the output and fonts folders, the pick, who holds the batch) that rebuild no rows.
- **The Job View drops `participants` and `start_time_ms`**, which the S4b part deferred to here: the rows say which items take part, and the clock and the elapsed labels are the core's. The Job View is `{job_id, mode, status, active, input_dir, effective_settings}`.
- **Superseded, their bodies unchanged**: ADR-0009 decision 2 (the heartbeat timer in `QueueTracker`) and its 2026-10-11 amendment (that timer redrawing the batch clock). Its rejection of "engine-emitted tick events across IPC" holds: the beat is the Desktop Core's, not the engine's, and the S4b patch of a beat carries only the processing rows and the clock (and the inspector when it shows one of them). ADR-0009 decision 4's formats are unchanged and are now `presentation.rs`'s.
- **Still the view's, outside S4**: the complexity slider's clamp and normalization, `subtitleAssignment` building a Track Assignment from the inspector's controls, and the empty list's title choice. Each is marked in the code as a rule the core could own.
