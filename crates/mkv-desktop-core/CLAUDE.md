# crates/mkv-desktop-core/CLAUDE.md

The Desktop Core side of the Engine Bridge. The webview frontend side is in `desktop-tauri/CLAUDE.md`.

## Engine ↔ desktop bridge

The bridge lives in `crates/mkv-desktop-core`: the active job in `job.rs` (`JobState`: the Job Slot, the supervisor, the two-phase stop), the `JobSnapshot` and its reducer in `snapshot.rs`, the Desktop Core actor in `actor.rs` (the Intents, the View State), the Job Coordinator and the Run preflight in `coordinator.rs`, the start of a Run and its Stop in `actor/start.rs`, the telemetry cadence and the Presentation Heartbeat in `actor/timers.rs` (the actor's tests in `actor/tests.rs`), every displayed value (row labels, tones, meta lines, filter buckets, the clock, counts, progress, Library, the job controls' and chips' texts) in `presentation.rs`, the Episode Inspector in `inspector.rs`, each mode's Run Log in `log.rs`, each mode's Settings Draft (its stepper and the `BatchRequest` a Run builds from it) in `draft.rs`, each mode's queue (Inspection Manifest, Queue Selection, Track Assignments, rows over a cached row base) in `queue.rs`, the Inspection Coordinator in `inspection.rs`, and the run, stop and shutdown logic in `control.rs` (with `EngineLauncher`, the actor's `Launcher` port adapter, which resolves, launches and stops on the blocking pool). Its tasks run on a tokio `Handle` the adapter passes to `JobState::new` and `Core::spawn`. In `desktop-tauri/src-tauri/src`, `commands.rs` and `process.rs` define the thin Tauri commands that call it (`dispatch`, `get_state`, `get_log`, `close_window`, …), and `publisher.rs` holds the `AppHandle` `Publisher`, which sends `view-state` as a patch of the state it emitted last (`view_patch.rs`). The engine streams `JobEvent`s and log lines over two tokio mpsc channels. A supervisor task forwards them through a `JobSink`, which in the app is the actor's `ActorSink` and in tests records them with no Tauri app. The supervisor reduces the events into its own private `JobSnapshot`, the settlement ledger it settles the job and computes `job-done` from, so teardown never depends on the actor. The actor reduces the same events with `JobSnapshot::apply_at` (the same reducer, on tokio's clock so paused-time tests move it) into the published snapshot, which carries the job's Effective Settings. It owns each mode's queue, scan, Settings Draft (the form's values as typed), Run Log and outcome, and the Job Coordinator, applies the Intents `dispatch` sends (a scan, a selection, a reorder, an `inspect` pick, a Track Assignment, a draft edit or `step_draft`, a Preset Profile, a Run, a Stop, a cache clear, the view's visibility), and publishes the whole View State (`{seq, job, run, busy, defaults, chips, presets, remux, extract, telemetry}`, `busy` being the phase not idle or a job active; each ModeView carries its rows' texts, the list header, `count_text`, `clock`, `progress`, `filters`, `library`, `inspector` and `controls`) at most every 66 ms, at once before a `dispatch` reply except to a draft Intent (`edit_draft`, `step_draft`, `set_preset`) or `view_visible` (coalesced by that cap), and before `job-done`. A Run answers once its start settles (resolve, forced scan, preflight, launch) and a Stop once its teardown is over; while a start or a job holds the batch, both queues and both drafts are locked and the user's scans are refused. Each mode's Run Log keeps its newest 2000 lines: a job's batches go to the job's mode, and the core writes the Run refusal, Stop, teardown and cache lines itself; a Run clears its mode's log once its request resolves. Each append or clear goes out at once as a `job-log` `LogBatch` (`{mode, generation, first, keep_from, errors, lines}`), and `get_log` reads a mode's whole log back. The core samples telemetry through its `Sampler` port every 1 s while busy and every 30 s otherwise, and not at all while `view_visible` says the window is hidden. The Presentation Heartbeat beats on each whole second of the job's clock while the batch clock runs (after a `BatchStart` naming items, until the batch ends) and the window is visible; a beat only marks the job's mode changed, and every publication presents the elapsed times and the clock as of then. It rebuilds only the ModeView of a mode that changed (a remux bitrate or assets dir edit changes remux, since the rows' meta lines name them), laying the status over each row's cached base. The core publishes no diff (a native view reads the state in-process); the webview adapter emits the first state whole and each later one as a patch, `{seq, base, ...changed keys}`, with a changed mode's rows as `rows` (whole, on a `manifest_rev`, length or id-order change) or `row_changes` (`[[index, Row], ...]`). `get_state` is always whole. A webview reload calls `get_state` and `get_log`, so it loses only view-local state (the open drawer, the scroll position).

Only one job runs at a time. Stopping is two-phase: a cooperative cancel with a 2 s wait, then an abort of the pipeline task.

Directory Identities that cross the bridge must use the display form of the canonical path, with the `\\?\` prefix stripped (`display_canonical_path`). That covers the identity a `ScanDirectory` Intent resolves the typed path to (`inspection::canonicalize_directory`), as well as `canonical_dir`, a ModeView's `directory`, the Job Snapshot's `input_dir`, and `BatchStart.input_dir`. The Desktop Core's queue and its Run preflight compare directories byte for byte and never normalize a path, so a mismatch silently breaks selection and ordering.
